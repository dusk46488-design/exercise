# Data Exploration Pipeline: Aggregation, Normalisation, and Completeness Analysis

## AI-Assisted Design Discussion

The exploration pipeline was designed through iterative dialogue with the AI, organised around three architectural questions. First, *what aggregations are relevant to the RS3 experiment?* The AI was prompted to reason from the experiment's distributional assumptions — ex-Gaussian RTs (Wagenmakers & Brown, 2007), logistic retention scores, and truncated-normal JOLs — to identify the statistical parameters that characterise each variable's central tendency, dispersion, and shape (skewness, kurtosis). Second, *how should normalisation be designed as a pluggable component, and why does the choice of method matter for downstream modelling?* The AI explained the sensitivity of Z-score standardisation to outliers (inflated variance estimates), the boundedness-preserving property of min-max scaling, and the robustness of median/IQR scaling for heavy-tailed data, locating peer-reviewed justification for each trade-off. Third, *what measures quantify "completeness" in a way that connects to the experiment's coverage goals?* The AI introduced Shannon entropy as a distributional-uniformity measure and Pearson correlation as a redundancy diagnostic, framing both within the information-theoretic tradition (Shannon, 1948; Cover & Thomas, 2006).

The resulting architecture extends the 0203 `FilterPipeline` with two new plugin interfaces: `FilterPlugin` (unchanged — DataFrame-to-DataFrame transforms for normalisation) and `AnalysisPlugin` (DataFrame-to-dict aggregations for descriptive statistics, outlier detection, and completeness diagnostics). Both plugin families are registered in a unified `AnalysisPipeline` that follows the same IPO pattern (load → filter chain → analyse → export metadata JSON), satisfying the exercise's requirement that all components remain pluggable.

## Aggregation Design and Motivation

### Key Statistical Parameters

The descriptive analysis plugin computes eight parameters per numeric column — count, missing count (and %), mean, median, standard deviation, minimum, maximum, skewness, and excess kurtosis — optionally grouped by a categorical variable such as `condition`. These parameters are chosen to directly evaluate the distributional assumptions of the RS3 data model:

| Parameter | What it verifies in RS3 |
|-----------|------------------------|
| **Mean / Median** | Central location of ex-Gaussian RTs (μ + τ) and logistic retention scores; discrepancy between mean and median signals skew |
| **Std** | Dispersion of RTs (σ component of ex-Gaussian) and test scores; the "law of response time" (SD ∝ mean) can be checked |
| **Skewness** | Right-tail heaviness of RT distribution (τ component); Fisher-Pearson skew > 0 confirms ex-Gaussian shape |
| **Kurtosis (excess)** | Tail weight relative to normal; elevated kurtosis in RTs indicates attentional-lapse outliers |
| **Missing %** | Quantifies the data loss from MCAR/MAR/MNAR injection; feeds into completeness assessment |

### Outlier Detection

Two complementary methods are implemented. The **IQR method** (Tukey, 1977) flags values outside [Q1 − 1.5·IQR, Q3 + 1.5·IQR] — non-parametric, ~0.7 % false-positive rate for normal data, and unaffected by the extreme values it detects. The **Z-score method** flags values with |z| > 3 — parametric, assumes approximate normality, and is sensitive to the very outliers it seeks to find (outliers inflate σ, shrinking all z-scores — the *masking effect*). Reporting both methods allows the analyst to cross-validate: IQR-only outliers that are not Z-score outliers typically indicate a heavy-tailed but symmetric distribution (consistent with ex-Gaussian), while Z-score-only outliers suggest a normal distribution with a few extreme points.

### Connection to Experiment Design

The RS3 experiment tests the hypothesis that spaced repetition produces a crossover interaction in retention scores (H1b: daily > spaced at Day 7, spaced > daily by Day 37). The aggregation grouped by `condition` directly evaluates this: the `retention_score` mean for `daily` vs. `spaced` at each `test_occasion` traces the predicted crossover. The `days_since_learning` × `retention_score` correlation (r ≈ −0.46) quantifies the forgetting slope, and the condition-stratified skewness reveals whether the distribution is compressed toward ceiling (negative skew) or floor (positive skew) — diagnostic of measurement range adequacy.

## Normalisation Design and Methodology

### Why Normalise?

Normalisation (feature scaling) transforms numeric columns to a common scale, preventing variables with larger numeric ranges from dominating distance-based algorithms. In the RS3 dataset, `trial_rt_ms` ranges from ~150 to ~30,000 ms while `retention_score` is bounded [0, 100]. Without normalisation, a k-means clustering or SVM would weight RT differences ~300× more heavily than score differences, despite both being equally relevant to the research question. Normalisation is a pre-processing step required by many statistical-learning algorithms: gradient descent converges faster on scaled features (LeCun et al., 2012), regularisation penalties (L1/L2) apply uniformly only when features are on comparable scales, and PCA variance decomposition is dominated by high-variance unscaled columns.

### Outlier Effects Before and After Normalisation

**Before normalisation:** Outliers exert a *dual* distorting effect on models. In distance-based methods (k-NN, k-means), a single extreme RT (e.g., 25,000 ms) creates a disproportionately large distance term that can reassign cluster centroids or misclassify neighbours. In variance-based methods (PCA, linear regression with OLS), outliers inflate the variance estimate, pulling the first principal component toward the outlier direction and increasing the leverage of the outlying observation.

**After normalisation:** The effect depends on the chosen method.
- **Z-score:** Outliers inflate σ, compressing all z-scores toward zero — the outliers remain visible (large |z|) but the bulk of the data is squeezed into a narrow range, reducing discriminative power.
- **Min-max:** A single outlier determines `max`, compressing all other values into [0, <0.01] — the worst-case distortion among the three methods.
- **Robust scaling:** Outliers have negligible effect on the median and IQR, so the bulk of the data is scaled to a well-separated range while outliers retain large (but finite) absolute values — the recommended method for heavy-tailed data such as ex-Gaussian RTs.

### Implemented Methods

Three normalisation filters are implemented as `FilterPlugin` subclasses, selectable via the `-f` CLI flag and chainable in any order:

| Filter | Formula | Strengths | Weaknesses |
|--------|---------|-----------|------------|
| **zscore** | (x − μ) / σ | Interpretable (units of SD); preserves rank; standard for PCA | Sensitive to outliers; assumes symmetric distribution |
| **minmax** | (x − min) / (max − min) | Bounded [0, 1]; preserves sparsity (zeros stay zero); standard for neural networks | Collapses under outliers; no centring |
| **robust** | (x − median) / IQR | Resistant to outliers; ~50 % breakdown point; appropriate for ex-Gaussian data | ~15 % efficiency loss vs. Z-score for truly normal data |

## Completeness Exploration

### Correlation Analysis

The completeness plugin computes the Pearson correlation matrix for all numeric column pairs. In the RS3 test data, the key structure is:
- `test_occasion` ↔ `days_since_learning`: r = 0.93 (expected — they encode the same temporal information)
- `retention_score` ↔ `jol_prediction`: r = 0.89 (strong metacognitive calibration — participants know what they know)
- `retention_score` ↔ `days_since_learning`: r = −0.46 (the forgetting curve — recall declines with time)

These correlations serve double duty: they validate that the generated data encodes the expected experimental structure, and they warn of multicollinearity (r > 0.9) that would destabilise regression coefficients if both variables were included as predictors.

### Information-Theoretic Completeness

Shannon entropy (binned histogram estimate) quantifies how uniformly a variable's values are distributed across its range. Low entropy indicates concentration (e.g., a ceiling effect where most scores are near 100); high entropy indicates near-uniform spread. In the RS3 data, `test_occasion` and `days_since_learning` have entropy ≈ 2.0 bits (four discrete values, near-uniform, consistent with the balanced design), while `retention_score` and `jol_prediction` have entropy ≈ 4.1 bits (spread across the [0, 100] range with moderate concentration).

Entropy is relevant to completeness because it captures *distributional coverage*: a dataset with high per-variable entropy spans more of the variable's support, providing better coverage of the population distribution. Comparing entropy before and after normalisation reveals how much the transformation reshaped the distribution — robust scaling should preserve entropy (it is a linear transform up to the median/IQR constants), while min-max scaling may reduce entropy if outliers are present.

### Coverage Assessment

The missing-data overview in the completeness report directly addresses the "coverage of the full population" question. For the RS3 test data:
- **89.7 % of rows are complete** (287 / 320) — the 10.3 % incomplete rows result from the combined MCAR (2 %), MAR (Day 97), MNAR (Day 37), and attrition injection mechanisms.
- **Only `retention_score` has missing values** (33 of 320, 10.3 %) — all other columns are fully observed, consistent with the injection design where missingness targets test scores specifically.
- **Condition-stratified missingness**: the `daily` group has 15.0 % missing retention scores vs. 5.6 % for `spaced`, reflecting the higher attrition probability assigned to daily-review participants in the generator design.

## Architecture Summary

The pipeline extends the 0203 **Backend → Model → Process** architecture with an `AnalysisPlugin` branch and a JSON input backend:

```
CLI (argparse)
  └─ AnalysisPipeline.process()                ← IPO function
       ├─ CSVBackend.load() / JSONBackend.load() ← Input layer (NEW: JSON reader)
       ├─ [FilterPlugin.apply() × N]            ← Normalisation chain (zscore/minmax/robust)
       ├─ JSONBackend.save()                    ← Output processed data
       ├─ [AnalysisPlugin.analyze() × M]        ← Aggregation layer (NEW)
       └─ JSONBackend.save_dict()               ← Output metadata report
```

**Backend layer** (`CSVBackend`, `JSONBackend`, `StatsHelper`): `JSONBackend` is extended with a `load()` method that reads JSON files (records, split, or dict format) into DataFrames, enabling the pipeline to ingest previously cleaned JSON output. `JSONBackend.save_dict()` serialises analysis results to a human-readable metadata report. `StatsHelper` is extended with `safe_skew`, `safe_kurtosis`, and `entropy` — all with edge-case handling for empty or constant columns.

**Model layer** (`FilterPlugin`, `AnalysisPlugin`): Two parallel ABC hierarchies. `FilterPlugin` (unchanged from 0203) defines the `apply(df) → df` contract for transforms; three normalisation filters implement it with distinct centring/scaling strategies. `AnalysisPlugin` (new) defines the `analyze(df) → dict` contract for aggregations; three analysis plugins produce descriptive statistics, outlier counts, and completeness diagnostics respectively. Both plugin families are registered at pipeline initialisation and discoverable via `--list`.

**Process layer** (`AnalysisPipeline`): The IPO function `process()` orchestrates the full pipeline: detect input format (CSV or JSON) → load → apply filter chain → save processed data → run analysis chain → save metadata report. The filter and analysis chains are independently specified at the CLI (`-f` and `-a`), enabling matrixed comparisons (e.g., compare descriptive stats before/after robust scaling, or run outlier detection on zscore-normalised vs. raw data).

## CLI Usage

```bash
# List all registered filter and analysis plugins
python 0204.py --list

# Descriptive statistics, grouped by condition
python 0204.py output/rs3_tests.csv \
    -a descriptive -g condition \
    -o output/rs3_tests_explored.json \
    -r output/rs3_tests_report.json

# Outlier detection on specific columns
python 0204.py output/rs3_trials.csv \
    -a outliers -c trial_rt_ms \
    -r output/outlier_report.json

# Full exploration: robust normalisation + all three analyses
python 0204.py output/rs3_trials.csv \
    -f robust \
    -a descriptive -a outliers -a completeness \
    -g condition \
    -o output/rs3_trials_normalised.json \
    -r output/rs3_trials_full_report.json

# Compare Z-score vs. robust normalisation
python 0204.py output/rs3_tests.csv -f zscore \
    -a descriptive -g condition \
    -r output/zscore_report.json
python 0204.py output/rs3_tests.csv -f robust \
    -a descriptive -g condition \
    -r output/robust_report.json

# Chained normalisation: robust first, then minmax (brings to [0,1] on outlier-resistant scale)
python 0204.py output/rs3_trials.csv \
    -f robust -f minmax \
    -a descriptive -a outliers \
    -r output/chained_report.json

# Ingest previously cleaned JSON (from 0203) instead of CSV
python 0204.py output/rs3_tests_clean.json \
    -a descriptive -a completeness \
    -r output/clean_exploration_report.json
```
