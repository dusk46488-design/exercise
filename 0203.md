# Data Filtering Pipeline: Design, Implementation, and Evaluation

## AI-Assisted Design Discussion

The filter architecture was developed through an iterative dialogue with the AI, focusing on three questions: (a) what detection mechanisms are appropriate for each type of data imperfection in the RS3 dataset, (b) how to structure the pipeline so that filters remain pluggable and independently evaluable, and (c) what statistical properties each method preserves or distorts. The AI was prompted to explain the theoretical foundations of complete-case analysis (Little & Rubin, 2019), median-imputation heuristics (Schafer, 1999), and hot-deck imputation (Andridge & Little, 2010), and to locate peer-reviewed references justifying each approach. The resulting architecture places each filter behind a common `FilterPlugin` interface (an abstract base class with a single `apply(df) → df` contract), registered in a `FilterPipeline` that chains filters in user-specified order. This design mirrors the plugin pattern described in the exercise brief: each filter is a self-contained, stateless component that can be activated, replaced, or combined without modifying the core IPO (Input → Process → Output) loop.

## Filter Designs and Applicability to the RS3 Experiment

### 1. Drop Filter — Complete-Case Deletion

**Design.** The drop filter removes any row where one or more values are missing (`NaN`), infinite, or empty-string — implementing *listwise deletion* (complete-case analysis). It inspects all columns by default but can be scoped to a user-specified subset via the `--columns` CLI flag.

**Applicability.** Complete-case analysis is applicable as a **baseline** for the RS3 experiment because the MCAR-injected rows constitute ~1–3 % of observations, well below the 5 % threshold where listwise deletion is generally considered acceptable (Schafer, 1999, p. 165). Under MCAR, the complete cases are a random subsample of the full dataset; parameter estimates remain unbiased, and only precision is reduced. The drop filter thus provides a clean, assumption-minimal reference point against which the heuristic and imputation methods can be compared.

**Implementation understanding.** The filter constructs a boolean mask by testing each cell against `notna()`, `np.isfinite()`, and non-empty-string criteria, then selects rows where the mask is `True` across all monitored columns. This is equivalent to `pandas.DataFrame.dropna()` with additional infinite-value detection for numeric columns — important because `np.inf` values are not captured by `dropna()` alone.

### 2. Heuristic Filter — Median/Mode Substitution

**Design.** The heuristic filter replaces missing values with column-wise central-tendency statistics: the **median** for numeric columns and the **mode** for categorical/object columns. It operates on all columns by default, preserving the row count at 320 (no rows are dropped).

**Applicability.** Median substitution is applicable as a **fast, deterministic intermediate** between deletion and model-based imputation. For the RS3 dataset's key variables — ex-Gaussian RTs (right-skewed) and logistic retention scores (bounded [0, 100]) — the median is more robust than the mean: it is unaffected by the heavy right tail of the ex-Gaussian and respects the bounded nature of test scores. The mode preserves the category frequencies for nominal variables such as `condition` and `session_type`. However, single-imputation methods systematically underestimate variance because they treat filled values as if they were observed (Little & Rubin, 2019, Ch. 4). The heuristic filter is therefore best understood as a **data-completion** tool (producing a rectangular dataset for analyses that cannot handle missing values) rather than a bias-correcting method.

**Implementation understanding.** The filter iterates over columns, computes `safe_median()` or `safe_mode()` on the non-missing subset, and calls `pandas.Series.fillna()` with the computed value. The `safe_*` helpers handle the edge case where an entire column is missing by returning `0.0` or `None`.

### 3. Imputation Filter — Hot-Deck Imputation

**Design.** The imputation filter identifies the **complete-case subset** — rows where no value is missing in the monitored columns — and draws replacements for missing values via random sampling with replacement from the observed values in that complete subset. This is **hot-deck imputation**: each missing cell is filled with a value that was actually observed elsewhere in the same column.

**Applicability.** Hot-deck imputation is applicable to the RS3 experiment because (a) the MCAR injection mechanism ensures that complete cases are a representative random sample, satisfying the "hot-deck donor pool is exchangeable with recipients" assumption (Andridge & Little, 2010, p. 63), and (b) it preserves the empirical distribution of each variable — including the right skew of RTs and the bounded range of test scores — without imposing parametric assumptions. For the RS3 data, where the ex-Gaussian RTs violate normality and retention scores are bounded [0, 100], hot-deck avoids the artefacts that regression-based or normally-distributed imputation can introduce. The filter falls back gracefully to median/mode substitution when no complete cases exist for a given column, ensuring robustness against edge cases.

**Implementation understanding.** The filter computes a complete-case mask (`notna().all(axis=1)`), extracts the observed values for each column from those rows, and uses `numpy.random.default_rng().choice()` with `replace=True` to draw `n_missing` samples. A fixed `--seed` (default 2026) ensures reproducibility.

## Architecture Summary

The pipeline follows the **Backend → Model → Process** layered architecture established in exercises 0201–02, extended with a **plugin registry** for filter components:

```
CLI (argparse)
  └─ FilterPipeline.process()           ← IPO function
       ├─ CSVBackend.load()             ← Input layer (new: JSON backend added as output)
       ├─ [FilterPlugin.apply() × N]    ← Process layer (pluggable filter chain)
       └─ JSONBackend.save()            ← Output layer (new file backend)
```

**Backend layer** (`CSVBackend`, `JSONBackend`, `StatsHelper`): Stateless I/O and statistical helpers. The `JSONBackend` is the new file backend required by the exercise, writing sanitised DataFrames as JSON arrays of records. `StatsHelper` provides `safe_median`, `safe_mode`, and `safe_mean` with edge-case handling (all-null columns, infinities).

**Model layer** (`FilterPlugin`, `DropFilter`, `HeuristicFilter`, `ImputationFilter`): An abstract base class defines the plugin contract (`apply(df) → df`). Each concrete plugin is a stateless callable configured at construction time. New filters can be registered at runtime via `FilterPipeline.register()`, satisfying the "pluggable component" requirement.

**Process layer** (`FilterPipeline`): The IPO function `process(input_csv, output_json, filters, columns)` orchestrates the full pipeline: load CSV, apply each named filter in order, save JSON. The filter chain is user-specified at the CLI, enabling A/B comparisons (e.g., `-f drop` vs. `-f heuristic` vs. `-f imputation`) without code changes.

**CLI entrypoint** (`main`): Uses `argparse` with positional `input`, optional `-o/--output`, repeatable `-f/--filter`, column subset `-c/--columns`, and reproducibility `--seed`. The `--list-filters` flag exposes the plugin registry to the user, supporting discoverability.

## CLI Usage

```bash
# List available filter plugins
python 0203.py --list-filters

# Apply the drop filter (complete-case analysis)
python 0203.py rs3_tests.csv -f drop -o rs3_tests_clean.json

# Apply the heuristic filter (median/mode fill)
python 0203.py rs3_tests.csv -f heuristic -o rs3_tests_heuristic.json

# Apply the imputation filter (hot-deck)
python 0203.py rs3_tests.csv -f imputation -o rs3_tests_imputation.json

# Chain filters: drop first, then impute any remaining missing values
python 0203.py rs3_tests.csv -f drop -f imputation -o rs3_tests_chain.json

# Filter only specific columns
python 0203.py rs3_trials.csv -f drop -c trial_rt_ms is_bogus -o rs3_trials_clean.json

# Reproducible imputation with a fixed seed
python 0203.py rs3_tests.csv -f imputation --seed 42 -o rs3_tests_imputed.json
```
